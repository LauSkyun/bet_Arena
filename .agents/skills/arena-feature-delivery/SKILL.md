# 功能开发与检查

先读[项目研发流程](../../../requirements/development-workflow.md)、当前 Raft 卡和该功能的讨论串，再按[需求索引](../../../requirements/README.md)定位模块。以确认的 `requirement.md`、卡片中适用的最新决策和范围为依据。实现记录和现有代码用于核实当前行为。若依据之间有冲突，写明来源和会改变的玩家结果，先推进可独立完成的部分。

## 开发与自测

1. 确认需求版本、涉及的模块和当前工作区变更。沿项目正常入口接通功能，按需求核对玩家可见结果及调用方依赖。对暂用固定返回的依赖，记录替代了什么、能验证什么。
2. 按本次条款选择验证。轮次、余额或状态涉及截止、刷新、重试与连续轮次时，复测受影响的时间、状态和余额边界。预期值来自需求。纯构建、空测试和实际用例通过分别记录。
3. 按[实现记录模板](../../../requirements/_template/implementation.md)更新模块的实现记录。交接时附可运行入口、代码版本、关键改动、自测结果和仍未验证的范围。未提交的本地版本可用可复算的源文件清单与哈希定位。

## 独立检查与返工复核

1. 核对提交或本地文件清单与实际运行产物，检查本次变更和必要的调用路径。对照“需求条款 → 代码实现 → 实测结果”。实现说明和开发自测用于定位，独立结论来自本轮实核。
2. 记录每项有判断价值的验证方式、环境、版本、结果和限制。区分开发自测、独立功能测试和待最终体验。验证条件缺失时，写清未执行的场景及原因，让接手人能接续。
3. 发现问题时，在功能讨论串说明对应条款、代码位置、预期与实测、影响和复现路径，在原卡保留结论和链接。复核修复时用修复版本复跑原场景与受影响的回归点。完成检查后按项目分工执行功能测试。

## 功能测试与整合交接

功能测试按需求场景从实际入口运行，记录版本、环境、步骤和观察结果。对时间、状态和余额等用户可见规则核对边界。从[测试档案](../../../testing/README.md)定位需求分析和 XMind 用例，把执行版本和结果留入运行档。把版本、测试结论和待联调的依赖记在功能卡，并更新[功能知识](../../../knowledge/README.md)。里程碑以同一个整合版本验证完整流程，按项目流程向 kaikai 提供统一入口。体验反馈按涉及模块留在对应功能讨论串。
