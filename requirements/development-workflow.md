# 竞猜竞技场研发流程

每个可独立验收的功能在 Raft 使用一个专属讨论串和一张任务卡。需求澄清、开发沟通、检查、返工和验收讨论都在该功能串。任务卡记录当前执行者、状态、阶段结论和证据入口，交接始终沿用原卡。当前由 Danny 写需求和开发，Cindy 做需求分析、代码检查、功能测试和修复复测，kaikai 体验里程碑整合版本。

## 正常交接

| 阶段 | 执行者 | 完成条件与下一步 |
| --- | --- | --- |
| 需求完成、建卡 | Danny → Cindy → Danny | Danny 交付功能的 `requirement.md`。Cindy 在项目频道新发一条以模块命名的消息，作为该功能的讨论串入口，从该消息建功能卡并指派 Danny。卡上写需求路径与版本、范围、验收场景、依赖和待确认事项。已建卡的功能补上独立串，在卡与串里互相链接。 |
| 开发、自测 | Danny | 按卡上版本实现，更新该模块的 `implementation.md`，按 [Git 规范](../CONTRIBUTING.md)交付可复核版本，在卡内附提交号、可运行入口、自测结果和已知偏差。交给 Cindy 检查。 |
| 需求分析、代码检查 | Cindy | 对照需求与验收场景检查功能和代码，重点看正常入口、关键规则、边界与相关回归。记录检查版本、覆盖范围和结论。通过后由 Cindy 继续功能测试。 |
| 功能测试 | Cindy | 从可运行入口按需求场景测试正常流程和关键边界。记录实测版本、环境、覆盖、结果及待联调的依赖，功能测试通过后由 Cindy 收口原功能卡。需求分析、XMind 用例与运行结果留在[测试档案](../testing/README.md)，稳定行为与迭代更新到[功能知识库](../knowledge/README.md)。 |

玩法与跨模块场景见[玩法总纲](overview.md)，模块需求和路径见[需求目录](README.md)。实现记录沿用[现有模板](_template/implementation.md)。影响玩家结果、验收口径或依赖是否可用的未决项，先在卡内明确并解决，再推进受影响的部分。若过程中确认要改规则，先由 Danny 更新需求并在卡内记录确认结果、版本和影响范围，之后以新版本检查和验收。

## 开发排期

开发排期由 Cindy 维护。Danny 完成一个模块的实现、自测和交接后，Cindy 按总纲和依赖安排下一个模块。前一个模块的检查和测试可并行推进。模块交接记录供开发和测试使用的实际版本与入口。前置问题如果影响后续模块，按受影响的范围安排或调整顺序。

## 里程碑 1 整合试玩

里程碑 1 的范围见[玩法总纲](overview.md)。Cindy 跟踪模块和联调进度，核对同一个整合版本从正常入口完成一整局，并验证结算后能继续下一轮。kaikai 准备体验时，Cindy 提供当时的进度和一个整合入口。达到里程碑时提交整局验证和体验入口，玩法反馈按涉及的模块在对应讨论串跟进。

## 返工

1. Cindy 检查或测试未通过，或里程碑体验发现需要返工的问题，由发现方在功能串记录需求条款、版本、复现步骤、预期、实测和影响，在原卡链接该问题，再把卡指回 Danny。
2. Danny 修复后回填改动版本、修复点和自测结果，把原卡再交给 Cindy。
3. Cindy 核对修复版本，复测原问题和受影响的功能。复测失败继续退给 Danny，通过后将修复纳入整合版本，并复跑受影响的整局流程。

## 卡片状态与记录

| 卡片状态 | 使用时机 |
| --- | --- |
| `todo` | 已建卡，等待开发开始。 |
| `in_progress` | 开发、检查、功能测试、返工和等待决策都使用此状态。当前阶段由执行者和指派理由说明。返工时指派 Danny。 |
| `done` | Cindy 已确认本功能测试通过，卡内有版本、测试结论和待联调范围。里程碑卡在 kaikai 确认整局体验后关单。 |
| `closed` | 功能确定取消、合并或作废，卡内记录原因及替代卡（如有）。 |

在本项目的 Raft v2 卡片上，验收交接使用「指派」。在指派理由里写清下一步，研发阶段按卡片当前执行者交接，里程碑体验交给 kaikai。需求版本、代码版本、检查和验收证据留在原卡或链接到项目文档。遇到依赖阻塞时，在卡内写明阻塞点、由谁解锁及预计时间，方便下一位接手。

## 功能卡收口

在原卡留下适用的需求段落、稳定的用例编号或 XMind 入口、实际验收记录、功能知识条目。各入口以相同版本交叉跳转。小修可复用对应功能的 XMind，并在独立报告注明补验；复测条件记录在报告中。还缺证据或未确认的事项在卡片里写清负责人和复验条件。

改动同一类战场信息时，沿用共享字段与显示规则，逐项核对受影响的匿名或账号战场、GM 布阵与自身回放、GM 导入重播。用同一对象及同一拍对照名称、颜色、等级或生命值；导入按文件保存的数据展示，缺失字段按对应需求处理。功能卡记录实际复测的入口和旧资料兼容结果。

## 需求确认与持续维护

- 项目成员从根目录 [AGENTS.md](../AGENTS.md) 找最新流程和技能。规范或技能更新后，Cindy 在项目讨论中同步变更、适用范围和入口，当前执行者回读并用于自己的任务。
- 在功能讨论串和原卡保留影响交付的问题、实证与处理结果。复盘后把可复用的改进写回对应的流程、模板或技能，并在[复盘记录](project-retrospectives.md)留下改动位置和验证根据。
- 有实质疑问或更好的方案时，先核当前依据，说明具体场景、影响、可选做法和建议。涉及玩法、范围、验收口径或阻塞选择时，及时请 kaikai 确认，同时推进可以独立完成的部分。已讨论清楚的改进可以先给 kaikai 一份简短结论并按确认结果落实。
